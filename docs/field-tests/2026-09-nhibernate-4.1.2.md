# Field test: NHibernate 4.1.2

Offramp was run against NHibernate, a large .NET Framework library shipped on NuGet, to find what
the fixtures and the first field test (DotNetNuke, an application) do not show. This page records
what happened, ranks what needs fixing, and gives the exact workaround that was needed, so each
item can become an issue.

- **Codebase:** [nhibernate/nhibernate-core](https://github.com/nhibernate/nhibernate-core) at tag
  `4.1.2.GA`, commit `4847062e1ecf729c610f1aa5bf14f39f9b4125f7` (the last 4.x release; .NET Framework
  4.0). An object-relational mapper, published as the `NHibernate` NuGet package.
  - **Solutions:** three, none at the root. `src/NHibernate.sln` has 5 projects: the library, its
    test project, a test domain model, a database setup project, and one Visual Basic test project.
    `src/NHibernate.Everything.sln` adds a console tool and an ASP.NET Web Site project.
    `Tools/BuildTool/BuildTool.sln` has one build tool.
  - **Size:** `src/NHibernate.sln` has 475,807 lines: NHibernate 264,478, NHibernate.Test 201,080
    (2,489 files, 802 embedded `.hbm.xml` mappings, 4,786 NUnit `[Test]` methods), the rest small.
  - **Projects:** all legacy (non-SDK) and `TargetFrameworkVersion v4.0`. No `packages.config`: 9
    third-party DLLs are checked in under `lib/` and referenced by `HintPath` (15 references). The
    library is strong-named with a checked-in key (`src/NHibernate.snk`).
  - **Build:** the official build is NAnt (`default.build`, `build-common/`). It generates
    `src/SharedAssemblyInfo.cs` and `.vb` (git-ignored, linked by 6 projects), then runs MSBuild on
    `src/NHibernate.sln`. In Release, NHibernate's `AfterBuild` runs `Tools/ilrepack/ilrepack.exe`
    to internalize Antlr3.Runtime and Remotion.Linq. The ANTLR parsers are generated by hand
    (`.bat` files) and checked in under `src/NHibernate/Hql/Ast/ANTLR/Generated/`.
- **Machine:** Ubuntu 24.04 in a container with 4 cores and 15 GB, the .NET 10.0.112 SDK from the
  Ubuntu archive, the .NET 8 runtime, and no Mono. Two other field tests ran on the same machine.
- **Offramp:** `main` at `5106c05` (v0.16.0 plus the DotNetNuke fixes), built locally and run as
  `dotnet src/Offramp.Cli/bin/Release/net10.0/offramp.dll`.
- **Method:** each command was run the way a new user would, following the README and
  `docs/compiling-on-macos.md`. Results were checked against the NHibernate sources, and the loose
  DLLs byte for byte against the packages on nuget.org. Root causes were traced in Offramp's code.
  Commands that write (`move extract`, `forwarders`, `deps resolve-dlls`, `csproj modernize`) were
  applied in scratch copies of the checkout and the result built with `dotnet build`.

## Summary

Out of the box, Offramp gets much further than on DotNetNuke. `doctor --fix --apply` writes the
legacy section of the compile-only block, and `scan` then fails on one missing file:
`src/SharedAssemblyInfo.cs`, which the NAnt build generates. With that file written, as
`CONTRIBUTING.md` tells every contributor to do, `scan` builds all 5 projects, the Visual Basic one
included, in 39 seconds with no diagnostics. The model is deterministic. Every command in the
standard sweep and every command tried after it ran to completion; none crashed.

However, NHibernate is a library, and most of Offramp's answers assume an application whose
consumers are all in the repository. The most serious results:

1. `audit dead-code` calls 250 public NHibernate symbols dead at **high** confidence: SQL dialects
   that users select by name in their configuration, `Configuration.AddXmlReader`,
   `DetachedCriteria.ForEntityName`, and more.
2. The three test projects reference NUnit through a `HintPath`, so they are classified as
   libraries. As a result, `audit dead-code` calls 249 NUnit fixture classes (20,966 lines) dead at
   high confidence, and `guide` tells the user to move the tests out of the test projects.
3. `move tests` plans to move `QueryOverBuilderExtensions`, a public extension class of the QueryOver
   API, out of the library into the test project, at high confidence.
4. `deps resolve-dlls` proposes Iesi.Collections **4.0.0.4000** for a DLL that is byte-identical to
   4.0.1.4000, and drops the `Debug`-only condition of two references. After `--apply` (exit 0),
   the solution no longer builds outside Windows: 2,505 errors.
5. `csproj modernize` rewrites `src/SharedAssemblyInfo.cs`, a git-ignored build output that a
   project outside the solution also compiles, and hard-codes its version numbers into 4 project
   files.

A library's goal is also not expressible where it matters. Its natural target is
`netstandard2.0` (NHibernate 5 did exactly that), but `--target` takes only a .NET major version.
`audit api` against net10.0 misses about 50 of the 71 errors that a `netstandard2.0` build of
NHibernate reports.

## What worked well

- **The legacy compile-only section:** on a .NET Framework 4.0 codebase with a Visual Basic project
  and no `packages.config`, the block that `doctor --fix --apply` writes was enough. The reference
  assemblies for net40 came from the package, and the VB project compiled with the
  `Microsoft.VisualBasic` wiring. No global property, symlink, or project edit was needed.
- **`scan`:** 39 seconds for 5 projects and 475,807 lines. `scan` and `scan --no-build` wrote the
  same model apart from `createdAt`, both on the fresh checkout and after the fix.
- **`init` and several solutions:** with three solutions and none at the root, `init --defaults`
  leaves `solution:` empty and lists the candidates (`OFR0020`, warning). `scan` without a solution
  stops with exit 2 and names them. `src/NHibernate.sln` is the right choice (the NAnt build and
  `CONTRIBUTING.md` use it), but `src/NHibernate.Everything.sln` looks just as plausible, so not
  guessing is right.
- **`audit api` attributions:** every one of the 188 findings names the API actually used at its
  location: `AppDomain.DefineDynamicAssembly`, `CallContext`, WCF's `OperationContext`,
  `System.Data.SqlClient`, CodeDom compilation, `BinaryFormatter`. The DotNetNuke-style
  misattribution (`System.Convert` "missing") did not occur. (Some of the rules applied to them are
  wrong; see [P1 #8](#8-audit-api-misjudges-securitycritical-and-callcontext).) The VB project is
  named as not audited (`OFR3012`).
- **`audit dead-code` reads mapping files:** classes named only in `.hbm.xml` mappings (for example
  `NHibernate.DomainModel.CustomPersister` in `Custom.hbm.xml`) are low confidence, with the file as
  evidence. The plugin-discovery rule found `typeof(ICompositeUserType).IsAssignableFrom(...)` and
  lowered the user types it discovers.
- **`audit serialization`:** it tells NHibernate's `SerializableType`, which stores
  `BinaryFormatter` output in database columns, apart from test-only deep clones (`OFR3203` vs
  `OFR3202`). Stored data is the part of a BinaryFormatter migration that needs a plan.
- **`audit native`:** no findings, which is correct: NHibernate has no P/Invoke or COM.
- **`ifdef report`:** 23 `NET_4_0` regions in 19 files, matching the sources.
- **`move extract` and `forwarders`:** `src/NHibernate/Proxy/DynamicProxy/` was extracted into a new
  `net40;netstandard2.0` project. 11 files moved with `git mv`, byte-identical (similarity 100%),
  and 12 files that do not compile on `netstandard2.0` (Reflection.Emit) stayed, each with its
  reason. Verification built the 6 affected projects. `forwarders --since HEAD` then wrote 11
  `TypeForwardedTo` attributes, and the solution built.
- **`csproj modernize --all` (dry run):** 3 of 4 C# projects converted with identical compile sets,
  including NHibernate's 1,693 compile items, now globbed, and NHibernate.Test's 805 embedded
  resources. The Release-only `AfterBuild` target was kept and renamed (`OFR4302`), conditional
  references were kept, and `AppendTargetFrameworkToOutputPath=false` keeps the legacy output
  folders.
- **`csproj modernize --tfm "net48;netstandard2.0"`:** the library's real goal can be written
  down, and the failed `netstandard2.0` build is the right to-do list (see [P1 #7](#7-a-librarys-target-netstandard20-is-not-expressible)).
- **`deps resolve-dlls`:** 4 of the 9 DLLs were matched to the right package: Remotion.Linq 1.13.183
  and Npgsql 2.2.7 are byte-identical to the nuget.org packages, and Antlr3.Runtime 3.5.1 is the
  closest published build of the checked-in 3.5.0.2.

## Findings, ranked

P0 means the command gives a wrong or dangerous answer. P1 means a gap that blocks real-world use.
P2 means polish. Each finding says whether it is general or specific to NHibernate.

### P0: wrong or dangerous results

#### 1. `audit dead-code` calls a shipped library's public API dead

`audit dead-code` reports 754 candidates in NHibernate, 269 at high confidence. 250 of those are
`public`, 2,962 lines, all with the evidence "public, and the assembly is not packed". Among them:

- `NHibernate.Dialect.MsSqlAzure2008Dialect`, `MySQL55InnoDBDialect`, `MySQL5InnoDBDialect`,
  `DB2400Dialect`, `OracleLiteDialect`, `SybaseASA9Dialect`, and the drivers `IfxDriver` and
  `DotConnectMySqlDriver`. Users select these by name (`<property name="dialect">`), and NHibernate
  loads them with `ReflectHelper.ClassForName`.
- `Configuration.AddXmlReader`, `AddDirectory`, `AddUrl`, `AddProperties`,
  `CurrentSessionContext.Unbind`, `DetachedCriteria.ForEntityName`, and
  `MySqlClientBatchingBatcherFactory`: public API that nothing in the repository calls because only
  users call it.

**Root cause:** `DeadCodeAnalyzer.Confidence` rates a public symbol `high` unless the project has
`IsPackable=true` or is listed in `deadCode.externalConsumers`. A legacy project never has
`IsPackable`. NHibernate is packed by NAnt from `src/NHibernate/NHibernate.nuspec.template`, and no
application in the solution references it: only tests do.

**Workaround:** `deadCode: { externalConsumers: [NHibernate] }` in `offramp.yml`. The 250 go to
`medium`, and the high-confidence total drops from 24,571 to 21,609 lines (the rest is
[P0 #2](#2-test-projects-that-reference-nunit-by-hintpath-are-libraries)). The setting is
documented only in `docs/spec/commands/audit.md`, not in `docs/spec/03-configuration.md`.

**Fix:** treat a project as shipped when any of these holds, and rate its public symbols `medium`
with evidence that says why:

- it is packable;
- a `.nuspec` or `.nuspec.template` sits in its folder, or a `.nuspec` names its DLL;
- it is a library that no non-test project in the solution references.

**General:** every legacy library packed with a `.nuspec`, and every repository whose libraries
are consumed elsewhere, gets this. NuGet libraries are a large share of what is still on .NET
Framework.

#### 2. Test projects that reference NUnit by `HintPath` are libraries

`NHibernate.Test` (4,786 `[Test]` methods, 1,009 `[TestFixture]` classes),
`NHibernate.Test.VisualBasic` and `NHibernate.TestDatabaseSetup` are `kind: library` with the
evidence `OutputType=Library`. They reference `lib/net/nunit.framework.dll` by `HintPath`.

**Root cause:** `ProjectKindDetector.Detect` recognizes a test project from `IsTestProject`, a test
`PackageReference`, a test package in `packages.config`, or the test ProjectTypeGuid. It has no rule
for assembly references, although `ProjectFacts.AssemblyReferences` carries them.
`GuideCatalog` has a list of test framework assemblies (`nunit.framework`, `xunit.core`,
`Microsoft.VisualStudio.QualityTools.UnitTestFramework`, ...) and uses it, so the guide knows these
are test projects while the model does not.

What follows from it:

- **`audit dead-code`** scans `NHibernate.Test` as production code: 1,802 candidates, 279 at high
  confidence. 249 of the 263 high-confidence classes are NUnit fixtures with `[Test]` methods, 20,966
  lines. The files of 245 of them have no `[TestFixture]` at all (NUnit 2.5 and later find a class by
  its `[Test]` methods), so the rule for attributed types does not lower them.
- **`guide`** lists the three test projects under "Move test code out of production projects" and
  proposes `move tests --project src/NHibernate.Test/NHibernate.Test.csproj --create`. That command
  plans `NHibernate.Test.Tests` and ends with 1,272 identical `OFR2104` errors. It also lists the VB
  project, which `move tests` refuses (`OFR2205`).
- **`slice --include-tests`** includes 0 test projects; **`plan`** and **`report`** count 5
  libraries to port; **`redirects sync`** sees no application; **`audit dead-code`**'s `testOnly`
  is 0 for the same reason.

**Fix:** move the guide's test-assembly list into `ProjectKindDetector` and add a rule
"Reference `nunit.framework`" (plus `xunit`, `MbUnit.Framework`, and the MSTest assemblies). Separately,
treat a type whose members carry a test attribute like one with a test attribute itself.

**General:** before NuGet, test frameworks were checked-in DLLs. Every older codebase that did not
migrate its test references has this.

#### 3. `move tests` moves public API out of the library

With `--to src/NHibernate.Test/NHibernate.Test.csproj` (see P2 for the default name), `move tests
--project src/NHibernate/NHibernate.csproj` plans one move at **high** confidence:
`src/NHibernate/Criterion/QueryOverBuilderExtensions.cs`, "used only by tests and other helpers",
"name suggests test support (QueryOverBuilderExtensions)". It also lists `WhereBuilder` (public) at
medium confidence.

`QueryOverBuilderExtensions` is a public static class of the QueryOver API: `Eager()`, `Lazy()`,
`Asc()`, `Force()` and so on, "to allow single-line statements on builders" (commit `13516f4`).
Nothing in NHibernate calls it; users do, and one test covers it (`QueryOverFixture.cs`). After the
move, the build and every test would pass, and the next NuGet package would silently lose the API.

**Root cause:** `TestCodeClassifier` classifies a helper from usage inside the solution and
`HelperNameHints` (`Builder`, `Fake`, `Stub`, ...), with no notion of a public surface that is
consumed outside it. This is the `Builder` heuristic from the DotNetNuke report, now with a
dangerous result.

**Fix:** never classify a public type of a shipped project (the rule in P0 #1) as test support;
at most list it as a low-confidence candidate with that reason.

**General:** any library.

#### 4. `deps resolve-dlls` picks an older package and drops conditions

The 9 checked-in DLLs, compared byte for byte with the packages on nuget.org:

| DLL | Offramp proposes | nuget.org |
|---|---|---|
| `lib/net/4.0/Iesi.Collections.dll` (assembly 4.0.0.0, file 4.0.1.4000) | Iesi.Collections **4.0.0.4000** | identical to **4.0.1.4000** |
| `lib/net/Remotion.Linq.dll` | Remotion.Linq 1.13.183 | identical |
| `lib/teamcity/postgresql/Npgsql.dll` | Npgsql 2.2.7 | identical |
| `lib/net/Antlr3.Runtime.dll` (file 3.5.0.2) | Antlr3.Runtime 3.5.1 | no identical file; 3.5.1 is the closest |
| `lib/net/System.Linq.Dynamic.dll` (unsigned) | System.Linq.Dynamic 1.0.0 | no identical file; plausible |
| `lib/teamcity/firebird/FirebirdSql.Data.FirebirdClient.dll` (2.5.2.0) | "is … from package 2.6.5" | nuget.org has no 2.5.2; 2.6.5 is an upgrade |
| `lib/net/log4net.dll` (1.2.10.0) | no match (`OFR1403`) | identical to log4net 1.2.10 (unlisted) |
| `lib/net/nunit.framework.dll` (2.6.1.12217) | no match | identical to NUnit 2.6.1 (package id differs) |
| `lib/teamcity/sqlServerCe/System.Data.SqlServerCe.dll` | no match | Microsoft.SqlServer.Compact (id differs) |

- **Wrong version.** NHibernate's history says "Update to Iesi.Collections 4.0.1" (`1705b37`).
  `--apply` would downgrade it in 3 projects. Both 4.0.0.4000 and 4.0.1.4000 ship assembly version
  4.0.0.0, and `DllResolver.FindPackageAsync` stops at the lowest package with the exact assembly
  version. The DotNetNuke fix (P0 #2 there) reads the version from `packages.config`, which a
  checked-in DLL does not have.
- **An upgrade presented as the same DLL.** The `OFR1402` message for Firebird says "is
  FirebirdSql.Data.FirebirdClient 2.5.2.0 from package FirebirdSql.Data.FirebirdClient 2.6.5"; only
  the `reason` field says "at or above".
- **Conditions dropped.** In `NHibernate.Test.csproj`, Antlr3.Runtime and Remotion.Linq are
  referenced with `Condition=" '$(Configuration)' == 'Debug' "`, because the Release build merges
  them into `NHibernate.dll` (`ilrepack.exe`). `DllResolver.Edit` removes the `Reference` and adds an
  unconditional `PackageReference`.

**Fix:**
- Rank candidate packages by an identical file (SHA-256 of the asset), then the same file version,
  then the same informational version, and only then by the lowest assembly version.
- Word the message by what matched: "is", "closest build", or "newer (an upgrade)".
- Carry the `Reference`'s condition, and its `ItemGroup`'s, to the new item.

**General:** checked-in DLLs are what `resolve-dlls` exists for, and packages that keep one
assembly version across releases are the norm (the DotNetNuke report lists six).

#### 5. `csproj modernize` rewrites a generated, git-ignored, shared file

For each of the 4 C# projects in the solution, the dry run lists `src/SharedAssemblyInfo.cs` among
the files it changes: it removes the three version attributes and writes
`<AssemblyVersion>4.1.0.4000</AssemblyVersion>`, `<InformationalVersion>4.1.2.GA</InformationalVersion>`
and `<FileVersion>4.1.2.4000</FileVersion>` into every converted project. Applied in a copy:

- `git status` shows nothing for the file, because `src/.gitignore` ignores `SharedAssemblyInfo.*`.
  The user cannot review the change.
- The NAnt build regenerates the file with the attributes on every build. With the SDK generating
  the same attributes from the new properties, the result is duplicate attributes (CS0579), and the
  version NAnt computes per release is frozen at 4.1.2.
- `NHibernate.Tool.HbmXsd`, which is not in `src/NHibernate.sln` and is not converted, compiles the
  same file and loses its version attributes.

**Root cause:** `ModernizePlanner.ConvertAsync` runs the `assemblyinfo` codemod over every source
file of the project's compilation and keeps its edits to files outside the project folder.

**Fix:** edit only AssemblyInfo files inside the project folder that no other project compiles, and
never a git-ignored file. For attributes that come from a shared or generated file, set the
matching `GenerateAssembly…Attribute=false` instead and say so.

**General:** a linked `SharedAssemblyInfo.cs`, `GlobalAssemblyInfo.cs` or `VersionInfo.cs` is
common in legacy solutions, and it is often generated by the build (NAnt, psake, Cake, GitVersion).

### P1: gaps that block real-world use

#### 6. `deps resolve-dlls --apply` is not verified, and its result does not build outside Windows

Applied in a copy, `deps resolve-dlls --apply --yes` exits 0 with `applied: true`. `dotnet build
src/NHibernate.sln` then fails with 2,505 errors (`CS0246: The type or namespace name 'Antlr' could
not be found`). Restore did resolve `Antlr3.Runtime/3.5.1` into `project.assets.json`.

**Root cause:** in a legacy project, turning a `PackageReference`'s `lib/` assets into compiler
references is the job of `ResolveNuGetPackageAssets` in Visual Studio's `Microsoft.NuGet.targets`.
The .NET SDK does not ship it. The compile-only legacy section restores legacy projects the
`PackageReference` way, so package *build* assets work (that is how the reference assemblies
arrive), but package *libraries* never reach the compiler. And `resolve-dlls` runs no restore or
build after writing, which CLAUDE.md requires ("`dotnet restore` verifies version choices").

**Fix:** verify `--apply` with the configured verification and roll back through the journal on
failure, as `move apply` does. Outside Windows, refuse to add a `PackageReference` to a legacy
project, and point to `csproj modernize` instead. Check `codemod run`, which also adds package
references to legacy projects.

**General:** any legacy project outside Windows. On Windows the same edit probably builds.

#### 7. A library's target (`netstandard2.0`) is not expressible

`--target` and `target:` take a .NET major version (`10` means `net10.0`). A library that must keep
serving .NET Framework users targets `netstandard2.0`, alone or next to `net48` (NHibernate 5 did).

- **`audit api`** audits against net10.0. NHibernate converted to `net48;netstandard2.0` (with
  `csproj modernize --accept-diff --apply` in a copy) builds for `net48` and fails for
  `netstandard2.0` with 71 errors in 25 files. About 50 of them are Reflection.Emit (`ILGenerator`
  ×21, `TypeBuilder` ×8, `MethodBuilder` ×6, `AssemblyBuilder` ×6, …), which net10.0 has and
  `netstandard2.0` does not. `audit api` reports none of them.
- **`guide`**'s port step proposes `csproj modernize --project src/NHibernate/NHibernate.csproj
  --tfm "net40;net10.0"` (`GuideCatalog.TargetFrameworks` appends `net{target}.0`).
- **`report`** says "applications 0" and has nothing to say about libraries.
- **`csproj modernize`**'s verification shows the first 10 build errors (`ModernizeVerifier`), with
  no total and no grouping.

**Fix:** accept a TFM wherever a target is taken (`--target netstandard2.0`, `target:
netstandard2.0`), with the integer as shorthand. For a shipped library (P0 #1's rule), have the
guide propose `<framework>;netstandard2.0` and `report` count libraries. In modernize's
verification, report the error count by code.

**General:** every library consumed by both .NET Framework and modern .NET applications, including
internal shared libraries in application repositories.

#### 8. `audit api` misjudges `[SecurityCritical]` and `CallContext`

- **`[SecurityCritical]`, `[AllowPartiallyTrustedCallers]`:** 23 of the 24 `OFR3009` findings are
  these attributes, all in NHibernate, as "error: COM+, CAS, and sandboxed AppDomains are gone;
  isolate the code in a separate process". Both attributes exist in `netstandard2.0` and net10.0
  and do nothing there; the `netstandard2.0` build above compiles all 22 uses. They sit on
  `GetObjectData` overrides, so every library with custom serializable exceptions has them.
- **`CallContext`:** `CallSessionContext` uses `CallContext.SetData`/`GetData`. It is reported
  twice at the same location, as `OFR3001` (missing) and `OFR3007` (.NET Remoting), with the
  remoting advice "use gRPC, HTTP, or named pipes (`offramp remote`)". The replacement is
  `AsyncLocal<T>` (NHibernate 5 added `AsyncLocalSessionContext`).
- **Generic advice where a known replacement exists:** `AppDomain.DefineDynamicAssembly` gets "See
  the assembly's mapping (`offramp deps gac`)"; the replacement is
  `AssemblyBuilder.DefineDynamicAssembly`.

**Root cause:** `rules/audit-api.yml`: `OFR3009` lists both attributes under `attributes`, and
`OFR3007` matches the whole `System.Runtime.Remoting` namespace.

**Fix:** move the two attributes to an info rule ("no effect on modern .NET; can stay"); add a
`CallContext` rule recommending `AsyncLocal<T>`; do not report `OFR3001` where a removed-technology
rule already matched the location. These findings also feed `seams`.

**General:** the attributes are in most libraries written for partial trust; `CallContext` is in
many web and logging code bases.

#### 9. `seams` on a library proposes moving 62% of it

`seams --project src/NHibernate/NHibernate.csproj` marks 1,470 of 2,355 types as tainted and
proposes an extraction of all 1,470 into `NHibernate.Windows`. The 13 seams it proposes
(`MappingDocumentParser`, `Dialect`, `HqlIdent`, …) have nothing to do with the unportable APIs.
Turning off `OFR3009` (P1 #8) only removes 25 types.

**Root cause:** 7 types that use an unportable API directly sit in one strongly connected
component of 979 types, the core of the ORM: `Cfg.Configuration` and `Cfg.Environment`
(`ConfigurationManager`), `ConnectionProvider` (`ConnectionStringSettings`), `ReflectionOptimizer`
(`SecurityManager`), `CallSessionContext` (`CallContext`), `WcfOperationSessionContext`, and the
CodeDom generator. `SeamsAnalyzer` taints every member of a component that contains a tainted type
(`seams.md` step 3). The component is built from every reference edge, calls included, although
step 2 says calls do not taint. Three of the seven are unportable only until the
`System.Configuration.ConfigurationManager` package is referenced, which the `OFR3001` finding itself
names.

The output is 14 MB of JSON, because the reason "in a reference cycle with …" lists every tainted
member of the component: 42,036 characters, repeated for 286 types.

**Fix:**
- Build the components from structural edges only (base types, and the types of fields,
  properties, parameters and return values of non-private members), so that calls stay places to
  cut.
- Do not count an API as unportable when a package supplies it on the target.
- When the extraction exceeds a share of the project (say a quarter), say so and list the directly
  tainted types instead.
- Name a cycle once and refer to it.

**General:** large libraries and monoliths with a service locator or a central configuration class
have one big component.

#### 10. `audit api-compat` cannot build a legacy project outside Windows

Without two targets, `audit api-compat` asks for `--baseline`, which is correct (`OFR3503`). With
`--baseline 4.1.1.GA`, both builds fail (`OFR3504`, exit 3):

- **The baseline** fails with MSB3644 (no net40 reference assemblies). Its scratch worktree has
  neither the compile-only `Directory.Build.props`, which is untracked in the working tree, nor the
  generated `SharedAssemblyInfo.cs`.
- **The working tree** fails with MSB3073 on `*Undefined*../Tools/ilrepack/ilrepack.exe`, because
  `ApiCompatRunner.BuildAsync` builds with `-c Release`. That configuration runs NHibernate's
  Release-only `AfterBuild`. The build also ignores `verify.configuration` and `verify.properties`.

**Fix:** build with `verify.configuration` and `verify.properties`. Give the baseline worktree the
compile-only sections that Offramp owns, and copy the git-ignored files that the working tree's
compilation used, with a note.

**General:** every legacy project outside Windows, and every project with a Release-only step
(ILMerge and ILRepack are common in libraries).

#### 11. `csproj modernize` fails a conversion because of a transitive project reference

`NHibernate.TestDatabaseSetup` references `NHibernate.Test`, which references
`NHibernate.DomainModel`. SDK-style projects pass project references on, so the converted project
compiles against `NHibernate.DomainModel` too. Verification reports it as "references added:
NHibernate.DomainModel" (`OFR4303`, `passed: false`).

**Root cause:** `CompileSets.Compare` counts as transitive only references from converted packages.

**Fix:** treat an added reference that is the output of a project in the ProjectReference closure
as transitive, or set `DisableTransitiveProjectReferences=true` in the converted project so that
the compile set stays identical (the more conservative choice).

**General:** any three-layer reference chain.

#### 12. `move extract` creates an unsigned project next to a strong-named one

The new `NHibernate.DynamicProxy` project is not signed. `NHibernate.dll` is signed
(`src/NHibernate.snk`) and now references it. The build and Offramp's verification pass, but on
.NET Framework a strong-named assembly cannot load an assembly without a strong name, so
NHibernate would fail at run time.

**Root cause:** `MoveExtractor` copies only `LangVersion`, `Nullable` and `ImplicitUsings`
(`CopiedProperties`) into the new project.

**Fix:** copy `SignAssembly`, `AssemblyOriginatorKeyFile` (rebased to the new folder), `DelaySign`
and `PublicSign`, and test extraction from a signed project.

**General:** strong naming is standard for libraries.

#### 13. An ASP.NET Web Site project stops the whole solution

`scan --solution src/NHibernate.Everything.sln` fails in 2 seconds with 0 projects loaded: MSB4249,
"Unable to build website project NHibernate.Example.Web. The ASP.NET compiler is only available on
the .NET Framework version of MSBuild." The solution metaproject stops before any project builds.
The `OFR0101` reasons then mislead:

- NHibernate: "no evaluation for it in the build log; MSBuild did not build it (check the solution
  configuration)".
- DomainModel: "not built: it references src/NHibernate/NHibernate.csproj, which failed". Nothing
  failed; nothing ran.
- The web site: "unsupported project type ()", with the type name missing.

**Workaround:** a solution filter without the web site. `scan --solution everything-noweb.slnf`
then loads 5 projects in 36 seconds.

**Fix:** the solution reader knows the Web Site type GUID (`E24C65DC-…`). Before building, build a
generated filter without Web Site projects and report each one as a Windows-only build step (a new
code next to `OFR0116`). Name the project type in `OFR0101`.

**General:** Web Site projects are common in older ASP.NET solutions. Specific to NHibernate only
in that its web site is a sample.

#### 14. A file the build generates is not detected

On a fresh checkout, `scan` fails with one error:
`CS2001: Source file '/…/src/NHibernate/../SharedAssemblyInfo.cs' could not be found` (`OFR0130`,
with an absolute path). Nothing says that the file is generated, that 5 C# projects link it (and the
VB project its `.vb` twin), or that `.gitignore` ignores it. NHibernate's compiler call failed, but
NHibernate is not in `partial`, and `audit api` audits it without a word. The other 4 projects are
partial, and `OFR3012` tells the user to "run `offramp scan`", which they just did.

**Fix:**
- Before building, report `Compile` items whose file does not exist, the way `OFR0117` reports a
  letter-case mismatch. When the path is git-ignored, say that the repository's own build probably
  generates it. This needs a new code.
- Mark a project partial when its compiler call failed.
- Name the build failure in `OFR3012`.

**General:** generated AssemblyInfo and version files are common with NAnt, psake, Cake, FAKE and
GitVersion.

### P2: polish

- **`deps audit` says nothing useful here.** It reports "0 packages" and "26 framework assembly
  references" without mentioning the 15 DLL references, and the guide marks `deps audit` not
  applicable. It should point to `deps resolve-dlls`.
- **`deps resolve-dlls` misses packages whose id differs from the assembly name** (NUnit ships
  `nunit.framework`; Microsoft.SqlServer.Compact ships `System.Data.SqlServerCe`) and exact versions
  that are unlisted (log4net 1.2.10). A small `rules/` table of assembly-to-package ids would cover
  the common cases.
- **`OFR1404` never fires for old DLLs.** 8 of the 9 DLLs have no `TargetFrameworkAttribute`, so
  none can be a blocker, although `System.Data.SqlServerCe` is .NET Framework-only native code. The
  referenced `mscorlib` version would tell.
- **An unsigned DLL is matched by package id alone** (System.Linq.Dynamic): any package with that
  id matches.
- **`csproj modernize --all` leaves the VB project out without a word.** `CsprojCommands` filters
  to C# before the planner, whose own refusal (`OFR4304`) is never reached.
- **`codemod run --mod sqlclient`** adds Microsoft.Data.SqlClient 7.1.0 to a net40 project; the
  package supports .NET Framework 4.6.2 and later. The dry run does not say so.
- **`audit serialization`** reports 753 `[Serializable]` types as never serialized (`OFR3205`),
  among them `NHibernate.Impl.SessionImpl`, while `OFR3204` says `NHibernate.ISession` is
  serialized. Implementations of a serialized interface, and the fields of serialized types, should
  count. For a library, users serialize its public types.
- **`audit behavior` has no rule for distributed transactions.** NHibernate's
  `AdoNetWithDistributedTransactionFactory` enlists in `System.Transactions`, and promotion to a
  distributed transaction works only on Windows, and only from .NET 7.
- **`move tests`** looks for `NHibernate.Tests`, although `NHibernate.Test` exists and references
  the project (`OFR2203`, exit 1 before any analysis). It reports a project-level failure once per
  file (1,272 × `OFR2104`). Both are DotNetNuke items that are still open.
- **`move extract`** rewrote `src/NHibernate.sln` through the solution serializer. The format
  changed from 11.00 to 12.00, and the `TestCaseManagementSettings` section (`NHibernate.vsmdi`) was
  dropped.
- **`report` mixes solutions.** After a scan of a filter and a scan of `src/NHibernate.sln`, it says
  "down 232 since" for two different solutions. The ledger snapshot records its solution.
- **`doctor`** checks the net48 reference assemblies package, while every project targets net40.
  Its "windows-only-build-steps: pass" does not see the Release-only `ilrepack.exe` step, because
  `scan` builds Debug.
- **Absolute paths** in `OFR0130`'s message and data and in `OFR0132`'s message.
- **The model keeps `NET,NET_2_0` as one symbol** in `defineConstants`; the compiler splits
  `/define` on commas. It is harmless here, since no `#if NET` exists in those projects.
- **The build phase has no heartbeat:** one progress event for 34 seconds (DotNetNuke, still open).
- **Two full scans differ in `source.sha256`**, the binary log's hash, so their models are not
  byte-identical apart from `createdAt`. `scan` and `scan --no-build` are.

## Appendix: what it took to get NHibernate through `scan`

Only the NAnt-generated file was needed; everything else came from `doctor --fix --apply`.

1. **`offramp.yml`:** `init --defaults`, then `solution: src/NHibernate.sln` (the solution that
   `default.build` and `CONTRIBUTING.md` use).
2. **`doctor --fix --apply --yes`:** writes the compile-only block, legacy section included, to
   `Directory.Build.props` at the root.
3. **The generated files.** Write what NAnt's `common.generate-assemblyinfo` target writes
   (`CONTRIBUTING.md`: "run the build menu and select option A"), with the values from
   `build-common/common.xml`:

   `src/SharedAssemblyInfo.cs`:

   ```csharp
   using System;
   using System.Reflection;
   using System.Runtime.CompilerServices;

   [assembly: AssemblyVersionAttribute("4.1.0.4000")]
   [assembly: AssemblyInformationalVersionAttribute("4.1.2.GA")]
   [assembly: AssemblyFileVersionAttribute("4.1.2.4000")]
   ```

   `src/SharedAssemblyInfo.vb`: the same three attributes in Visual Basic
   (`<Assembly: AssemblyVersionAttribute("4.1.0.4000")>`, …).

For `src/NHibernate.Everything.sln`, also use a solution filter that leaves out
`NHibernate.Example.Web` ([P1 #13](#13-an-aspnet-web-site-project-stops-the-whole-solution)).

The byte comparisons in P0 #4 downloaded each candidate `.nupkg` from
`https://api.nuget.org/v3-flatcontainer/` and compared SHA-256 hashes of the DLLs.
