# Field test: Open Live Writer 0.6.3 (master)

Offramp was run against a real WinForms desktop application to find the gaps that the fixtures and
the DotNetNuke field test do not show. This page records what happened, ranks what needs fixing,
and gives the exact workarounds that were needed, so each item can become an issue.

- **Codebase:** [OpenLiveWriter/OpenLiveWriter](https://github.com/OpenLiveWriter/OpenLiveWriter),
  branch `master` at `1f7fbca359d9cfa5502466b360b016cc8b8b9d80` (5 August 2026; `version.txt` says
  0.6.3.0). Not a tag: `v0.7.0` is the .NET 10/Avalonia port, and `0.6.2.0` is from 2017, so master
  is the latest .NET Framework-only state.
- **Shape:** a WinForms blogging client. `src/managed/writer.sln` has 30 entries: 28 C# projects,
  one native C++ project (`src/unmanaged/OpenLiveWriter.Ribbon/OpenLiveWriter.Ribbon.vcxproj`, a
  resource-only DLL compiled from Ribbon markup with `UICC.exe`), and a solution folder. The
  repository has 38 `.csproj` files, all legacy (two in the Visual Studio 2003 format, outside the
  solution), two more native `.vcproj` projects outside the solution, and 9 `packages.config` files
  (22 package versions). 27 projects target .NET Framework 4.6.1 through the shared
  `writer.build.settings`; `LocEdit` targets 4.7.2. The repository has 412,000 lines of C#; the 28
  solution projects compile 327,159. 21 of the 28 reference WinForms. `OpenLiveWriter.Interop`
  compiles 302 P/Invoke declarations, and 244 `[ComImport]` interfaces wrap MSHTML and the shell.
  Two test projects use MSTest v1 (`Microsoft.VisualStudio.QualityTools.UnitTestFramework`).
- **Machine:** Ubuntu 24.04 in a container with 4 cores and 15 GB of RAM, the .NET 10.0.112 SDK from
  the Ubuntu archive, the .NET 8 runtime, and no Mono. Two other field tests shared the machine.
  The sandbox proxy blocks `globalcdn.nuget.org`, where nuget.org's v2 feed (the one OLW's
  `NuGet.config` names) redirects package downloads; `api.nuget.org` works.
- **Offramp:** `main` at `5106c05` (v0.16.0, after the DotNetNuke fixes), built locally and run as
  `dotnet src/Offramp.Cli/bin/Release/net10.0/offramp.dll`.
- **Method:** each command was run the way a new user would, following the README and
  `docs/compiling-on-macos.md`, with `--json`, from the repository root. Every result below was
  checked against the OLW sources, and the root cause was traced in Offramp's code where it was not
  obvious. Two probes used a second state folder (`paths.state`) so the main model stayed intact.

## Summary

Out of the box, `scan` fails after 210 seconds: 25 of the 26 C# projects MSBuild reaches stop with
MSB3644 (no reference assemblies for .NET Framework 4.6.1). `doctor --fix --apply` wrote the
compile-only block, but OLW's `writer.build.settings` overrides `MSBuildExtensionsPath`, so no project
ever imports `Directory.Build.props`. Nothing says so, and `OFR0130` reports "2 error(s)". Getting a
clean build took ten fixes to OLW's build, plus one for this sandbox's proxy, all listed
[below](#appendix-what-it-took-to-build-olw-on-linux). Offramp named five of the ten; for two of
those five, the documented remedy did not work as written.

With the workarounds, `scan` succeeds in 40 to 66 seconds: 28 projects, the native project reported
as not loaded, and a model that `scan --no-build` reproduces byte for byte apart from `createdAt`.
Every command then ran to completion: no crash, no `OFR0099`, exit codes 0 and 1 only. The standard
sweep took about 9 minutes. However, several commands give **wrong answers** on a desktop codebase:

1. `audit api` compiles 18 of the 21 projects that use WinForms (15 of them class libraries) for
   `net10.0` instead of `net10.0-windows`. 13,374 of its 13,910 "API missing on target" findings
   (96%) are WinForms and System.Drawing APIs that exist on `net10.0-windows`. Compiled for
   `-windows`, 441 remain, and the 102 uses of `MenuItem`, `ContextMenu`, `Menu` and `DataGrid`,
   which throw on .NET 10, are then not reported at all.
2. `audit dead-code` marks the plugin SDK's public API (`WriterApplication`, `PluginDiagnostics`,
   `TaskServices`, shipped by `OpenLiveWriter.SDK.nuspec`) and methods that JavaScript calls on a
   `[ComVisible]` object as dead at **high** confidence.
3. `csproj modernize --project` (the guide's per-project step) edits `GlobalAssemblyInfo.cs`, which 20
   projects compile. The 19 projects it does not convert lose `AssemblyProduct` and
   `AssemblyCompany`, and verification cannot see it.
4. `deps resolve-dlls` proposes `System.Resources.Extensions` **4.6.0** for a 6.0.0 DLL and writes it
   into 28 project files, although `Directory.Build.props` declares the reference. This is the
   reference that `OFR0119`'s documented fix asks for.
5. `csproj modernize --all` fails verification for all 28 projects, for reasons Offramp could
   handle: an assembly-version file generated by the build, a package downgrade across converted
   projects, and a scratch copy that lacks the working tree's changes.

The common thread is that desktop applications and hand-written MSBuild customization (shared
`.settings` files, build-time generators, solution-level dependencies, native projects) are not
covered by the fixtures. Real WinForms codebases are made of them.

## What worked well

- **The DotNetNuke fixes for `packages.config` hold.** `scan` restored all 22 package versions into
  `src/managed/packages/` (`OFR0106`). `deps audit` sees 21 packages, and each verdict matches the
  package's `lib/` folders. `deps consolidate` names the real skew (`OFR1204`: Newtonsoft.Json 13.0.1
  in `BlogClient`, 10.0.2 in `PostEditor`). `deps resolve-dlls` recognized all 92 `packages.config`
  HintPaths and changed no version. `redirects sync --prune` pruned nothing and moved the
  Newtonsoft.Json redirect from 10.0.0.0 to 13.0.0.0 in the four applications, which is what
  `AutoGenerateBindingRedirects` produces at build time. No ledger snapshot was written for a failed
  scan.
- **Determinism:** `scan` and `scan --no-build` produced identical models apart from `createdAt`.
- **Build-step diagnostics that fired were right:** `OFR0117` named `intl/markets/Master.xml` (on disk
  `master.xml`) and the `Video/YouTube` folder (on disk `Youtube`). `OFR0115` named both `Exec`
  failures, and its remedy (a condition on the `PostBuildEvent` property group) works for the
  installer project. `OFR0119` named the first project with image resources.
- **`audit native`, `audit behavior`, `audit serialization` are accurate.** The 314 P/Invoke findings
  and 244 COM interop findings equal the declarations in the compiled files, and uncompiled files on
  disk are left out. `audit behavior` found the 11 `Process.Start(url)` calls that stop opening URLs
  on .NET, and the `process-start-url` codemod rewrites exactly those 11 sites (dry run).
  `BinaryFormatter` in `CoreServices/Settings/RegistryCodec.cs` is flagged as persisted binary
  serialization (`OFR3203`), which is correct: it stores settings in the registry.
- **`audit dead-code` understands WinForms wiring.** Event handlers attached in `InitializeComponent`
  are not candidates. The 10 handlers it flags at high confidence were each checked, and none is
  attached anywhere. Built-in plugins, registered with `typeof(...)`, are not candidates.
- **`csproj modernize` keeps what a WinForms executable needs:** `ApplicationIcon`,
  `ApplicationManifest`, `StartupObject`, `OutputType=WinExe`, `.resx` items with `Generator` and
  `LastGenOutput`, `DependentUpon` designer files, `Content` items, and the repository's own imports.
- **`audit api` attribution (DotNetNuke P0 #1):** no finding blames `System.Convert`,
  `System.Exception` or OLW's own types. A residue is described under P0 #1.
- **`plan`, `graph`, `report`, `guide`, `doctor`** answer in about a second each.

## Findings, ranked

P0 means the command gives a wrong or dangerous answer. P1 means a gap that blocks real-world use.
P2 means polish. Each finding says whether it is general or specific to OLW.

### P0: wrong or dangerous results

#### 1. `audit api` compiles WinForms libraries for `net10.0` (TargetCompilationBuilder)

`TargetCompilationBuilder.BuildUncachedAsync` compiles a project for `-windows`, with
`Microsoft.WindowsDesktop.App`, only when `project.Kind is Winforms or Wpf`. `ProjectKindDetector`
gives that kind only to `UseWindowsForms`/`UseWPF` projects and to `WinExe` projects that reference
`System.Windows.Forms`. In OLW that is 3 of the 21 projects that reference WinForms. The other 18
(15 class libraries full of forms and controls, two console tools, a test project) are compiled for
plain `net10.0`.

- Of 13,910 `OFR3001` findings, 11,010 are `System.Windows.Forms` and 2,364 `System.Drawing` (96%),
  in 19 projects: `System.Windows.Forms.Control` ×3,502, `Form` ×973, `AnchorStyles` ×624, and so
  on. The message contradicts itself: "`Control.SetStyle` (System.Windows.Forms) does not exist on
  the target. The assembly is part of the target, but not this API. Target net10.0-windows with
  `<UseWindowsForms>true</UseWindowsForms>`."
- It reaches the application too. `OpenLiveWriter.csproj` is compiled for `-windows`, but it
  references the libraries' `net10.0` compilations, so `OpenPostForm.ShowDialog(...)` in
  `ApplicationLauncher.cs:244` becomes a finding (it disappears in the probe below).
- `OFR3002` (Windows-only API, 140 findings: registry, `Marshal` COM helpers) is only raised because
  the libraries are compiled for `net10.0`. The spec says desktop projects get none.
- The same kind test decides `-windows` elsewhere: `GuideCatalog.TargetFrameworks` (the guide's
  `csproj modernize --tfm` suggestion) and `seams`, whose taint comes from these findings (510 of
  `PostEditor`'s 857 types are tainted; 290 of them only by WinForms or System.Drawing).
- **Probe:** with those 18 projects overridden to `kind: winforms` in `offramp.yml`, `OFR3001` drops
  from 13,910 to 441 (397 of which are the MSTest v1 projects, P1 #8) and `OFR3002` to 0.
- **The fix must keep what is really missing.** On `net10.0` the audit reported `MenuItem` ×77,
  `ContextMenu` ×12, `Menu` ×11 and `DataGrid` ×2. .NET 10's reference assemblies contain these
  types as binary-compatibility shims marked `[Obsolete(DiagnosticId = "WFDEV006")]` that throw at
  run time, so on `-windows` they compile and the probe reports none of the 102.
- **Residue of DotNetNuke P0 #1:** 63 findings name members that exist on the target:
  `System.ComponentModel.Component.DesignMode` ×45, `Component.Events` ×14, `Dispose()`, `Disposed`.
  They are inherited through the missing `Control`. `TargetCompilationMatcher.BindsOnTarget` only
  asks whether the name binds at that position, which it cannot when the base class is missing.
- **Fix:**
  - Decide `-windows` from the project's references (`System.Windows.Forms`,
    `PresentationFramework`, `WindowsBase`, `System.Xaml`) and `UseWindowsForms`/`UseWPF`, not
    from its kind. Put the rule in one place that the audit, the guide and `csproj modernize` share.
  - Report symbols carrying `ObsoleteAttribute` with `DiagnosticId` `WFDEV006` (or a
    `rules/*.yml` list of the shim types) as `OFR3003`, "throws on modern .NET".
  - In `BindsOnTarget`, also accept a recorded symbol whose containing type exists in the target's
    references.
- **General:** every WinForms or WPF codebase keeps its forms and controls in class libraries.
- **Regression fixture:** a WinForms class library with a `UserControl` that calls
  `SetStyle(...)` and uses `DesignMode` and `MenuItem`.

#### 2. `audit dead-code` removes a plugin SDK and script-called COM members (DeadCodeAnalyzer)

`DeadCodeAnalyzer` rates a public symbol `high` unless the project sets `IsPackable` or is listed in
`deadCode.externalConsumers`. Two kinds of live code in OLW fail that test:

- **The plugin SDK.** `OpenLiveWriter.Api` is the API third-party plugins compile against. It ships
  as the `OpenLiveWriter.SDK` NuGet package through `OpenLiveWriter.SDK.nuspec` at the repository
  root (`<file src="src\managed\bin\Release\i386\Writer\OpenLiveWriter.Api.dll" .../>`). Offramp
  rates 5 of its symbols `high` (257 lines): `WriterApplication`, `PluginDiagnostics`,
  `TaskServices`, `HtmlServices.HtmlDecode`, `PluginHttpRequest.GetWriterProxy`. The evidence reads
  "public, and the assembly is not packed". Legacy projects are never `IsPackable`, and standalone
  `.nuspec` files were how packages were made before SDK-style projects.
- **COM-visible types.** 7 high-confidence candidates are public methods of `[ComVisible(true)]`
  classes (`JSMapController`, `MshtmlControl`, `ContentEditorFactory`). Three of them,
  `JSMapController.NextEvent()`, `SetCenter(...)` and `JSUpdateBirdsEye(...)`, are called from
  JavaScript in `OpenLiveWriter.InternalWriterPlugin/map.html` (`jsMapController.NextEvent()`,
  lines 172 to 247 and 340) through the browser's `window.external`. `.html` and `.js` files are not
  string sources, and `[ComVisible]` is not a reflection attribute to the analyzer.
- **Fix:**
  - A project whose output assembly a `.nuspec` names (or with a `.nuspec` beside it) is packed:
    `medium`.
  - A public member of a `[ComVisible(true)]` type (or of an assembly marked `ComVisible(true)`) is
    reachable by COM and script clients: `low`, with that reason.
  - Read `.htm`, `.html` and `.js` files as string sources, like markup.
- **General:** standalone `.nuspec` files are common in .NET Framework codebases, and
  `ObjectForScripting` and COM servers are common in desktop applications.

#### 3. `csproj modernize --project` edits a source file that other projects compile

Converting only `OpenLiveWriter.Localization` (dry run, `--tfm "net461;net10.0-windows"`) removes
`AssemblyProduct` and `AssemblyCompany` from `src/managed/GlobalAssemblyInfo.cs` and moves them to
`<Product>` and `<Company>` properties in the converted project. That file is linked into 20
projects. The 19 that stay legacy do not generate assembly attributes, so their assemblies lose
Product and Company. Verification builds only the converted project, so it cannot notice.

The guide's "port" step runs `csproj modernize --project ... --tfm ...` one project at a time, so the
guided path is the one that does this.

- **Fix:** when a file with attributes the SDK generates is compiled by any project not being
  converted, leave the file alone and set `GenerateAssemblyProductAttribute` and its siblings (or
  `GenerateAssemblyInfo`) to `false` in the converted project. Report it with `OFR4302`.
- **General:** a shared `GlobalAssemblyInfo.cs` or `SolutionInfo.cs` is the norm in multi-project
  .NET Framework solutions (DotNetNuke has one too).

#### 4. `deps resolve-dlls` guesses the version of a DLL outside the repository

This was found by following `OFR0119`'s documented fix (P1 #6): a `System.Resources.Extensions`
reference for all legacy projects, declared once in `Directory.Build.props` with
`<HintPath>$(NuGetPackageRoot)system.resources.extensions/6.0.0/lib/net461/...</HintPath>`.

- `ProjectModelBuilder` keeps only the file name of a HintPath outside the repository
  (`"hintPath": "System.Resources.Extensions.dll"`) and reads no metadata from it.
- `DllResolver` then picks the lowest package version that ships an assembly of that name: OFR1402
  "System.Resources.Extensions.dll is System.Resources.Extensions  from package
  System.Resources.Extensions 4.6.0" (the version in the message is empty), ×28.
- The `--apply` preview adds `<PackageReference Include="System.Resources.Extensions"
  Version="4.6.0" />` to all 28 project files. The reference is not in those files, so it would
  remain and be duplicated.
- The MSTest.TestFramework 1.4.0 references declared the same way (two DLLs in two projects) become
  `OFR1403` "matches no project or package".
- **Fix:**
  - Read the metadata of a HintPath that exists on disk, wherever it is. Take the id and version
    from a path under the NuGet global packages folder (`<root>/<id>/<version>/`), as the DotNetNuke
    fix does for `packages/<Id>.<Version>/`. Without an assembly version, do not propose a version.
  - Only rewrite references the project file itself declares (`DefiningProjectFullPath`); report
    the others with the file that declares them.
- **General:** references in shared `.props`/`.settings` files are common, and a HintPath into the
  global packages folder is the only way a legacy project gets a package's DLL under the .NET SDK.

### P1: gaps that block real-world use

#### 5. The compile-only block silently misses every project

- `writer.build.settings`, which every OLW project imports first, sets
  `<MSBuildExtensionsPath>$(MSBuildToolsPath)\MsBuildExtensions</MSBuildExtensionsPath>`
  ("prevent accidental pickup of local-machine scripts"). OLW projects never import
  `Microsoft.Common.props` themselves, and the fallback import in
  `Microsoft.Common.CurrentVersion.targets` goes through `$(MSBuildExtensionsPath)`. So
  `Directory.Build.props`, and with it the whole compile-only block, is never imported (checked
  with `dotnet msbuild -getProperty`: `OfframpCompileOnly` empty, `MSBuildProjectExtensionsPath`
  empty).
- Result: MSB3644 in 25 projects. The 26th, `LocEdit`, is the only project that does not import
  `writer.build.settings`: it got the block and its reference assemblies.
- Importing the block late, from `Directory.Build.targets`, is no workaround: the restore then fails
  with "Value cannot be null (Parameter 'path1')", because `MSBuildProjectExtensionsPath` is empty.
- **Nothing names it.** `doctor`'s `OFR0018` only checks that `Directory.Build.props` contains the
  legacy section, and its reference-assemblies check passes.
- **`OFR0130` undercounts:** "The build failed with 2 error(s) (MSB3644 ×1, MSB4278 ×1)".
  MSBuild's own summary says 28 errors. `ScanRunner.ReportBuildErrors` dedupes on
  `(Code, File, Line, Message)`, and `File` is the shared targets file, so 25 projects collapse to
  one.
- **Fix:**
  - After the build, outside Windows, check each legacy project's evaluation for
    `OfframpCompileOnly`. When it is missing, raise a new diagnostic naming the cause: the project
    does not import `Microsoft.Common.props` and `MSBuildExtensionsPath` is overridden (in which
    file), `ImportDirectoryBuildProps` is false, or a nearer `Directory.Build.props` does not import
    the root one.
  - `doctor` can run the same check from the model.
  - `OFR0130`: dedupe per project and say how many projects each code affects.
- **General:** the override is OLW's (it comes from Microsoft's internal build system). A nested
  `Directory.Build.props` that does not chain to the root is common, and has the same effect.

#### 7. A solution-level dependency on the native project hides the application

`writer.sln` gives `OpenLiveWriter.csproj`, the application, a `ProjectSection(ProjectDependencies)`
on `OpenLiveWriter.Ribbon.vcxproj`. The native project fails evaluation outside Windows (MSB4278), so
MSBuild never builds the application or `PostBuild.CreateInstaller`, which depends on both.

- `OFR0101` says "no evaluation for it in the build log; MSBuild did not build it (check the
  solution configuration)". Both are in `Debug|Any CPU`. `ScanRunner.FailedReference` reads only
  `ProjectReference` items, not the solution's dependencies.
- When the restore failed (scan 08, a blocked feed), all 28 C# projects got `OFR0101`, as
  "not built: it references X, which failed" or "check the solution configuration", although the
  build never started. `OFR0130` then read "failed with 3 error(s) ( ×3)": NuGet errors have no
  code.
- **Fix:** read `ProjectModel.Dependencies` from Microsoft.VisualStudio.SolutionPersistence and
  include them in `FailedReference`. When the log has restore errors, give "the restore failed"
  (with the first error) as the reason. Give a codeless error a label such as `restore`.
- **General:** solution-level dependencies are how mixed native and managed solutions order their
  builds.

#### 8. Native and MSTest v1 projects are misclassified

- **The native project is a .NET Framework library in the model** when MSBuild evaluates it. In the
  as-shipped scan, `OpenLiveWriter.Ribbon.vcxproj` has `language: other`, `kind: library`,
  `frameworkClass: framework` (`Tfm.Classify` returns `framework` for no target frameworks) and 0
  lines. `plan` puts it in wave 1 as `ready`, and `report` counts it among 27 framework projects.
  Once the build no longer evaluates it, it is `OFR0101` "unsupported project type (.vcxproj)"
  instead. The two `.vcproj` projects are outside the solution.
- **MSTest v1 projects are libraries.** `OpenLiveWriter.UnitTest` (135 `[TestMethod]`) has no test
  `ProjectTypeGuids` and no test package, only a `Reference` to
  `Microsoft.VisualStudio.QualityTools.UnitTestFramework`, so `ProjectKindDetector` calls it a
  `library`. The guide then proposes `move tests --project OpenLiveWriter.UnitTest --create`, and its
  dry run plans 16 moves into a new `OpenLiveWriter.UnitTest.Tests`. `GuideCatalog` already lists
  that assembly as a test assembly; the kind detector does not.
- **Fix:** a project that is not C#, Visual Basic or F# is never in the model's framework counts or
  the plan. Name it once (`OFR0101` or an info code), whether or not MSBuild evaluated it, and call
  out C++/CLI (`CLRSupport`), which does need migrating. In `ProjectKindDetector`, count references
  to test framework assemblies (`Microsoft.VisualStudio.QualityTools.UnitTestFramework`,
  `nunit.framework`, `xunit.core`), not only packages.
- **General:** solutions with native projects are common in desktop codebases, and so is MSTest v1.

#### 9. `csproj modernize --all`: 28 of 28 conversions fail verification

The dry run on all 28 projects reports `OFR4303` for every one: first error CS0579 in 20, NU1605
in 5, a restore failure in 2, MSB3073 in 1. None of the causes is the conversion of the project
itself:

- **Duplicate assembly attributes (CS0579), 20 projects.** `writer.build.targets` generates
  `GlobalAssemblyVersionInfo.cs` from `version.txt` before `CoreCompile`. The SDK now also generates
  `AssemblyVersion` and `AssemblyFileVersion`. The converter removes such attributes from source
  files (the `assemblyinfo` codemod), but this file only exists at build time.
- **Package downgrade across converted projects (NU1605), 5 projects:** `PostEditor` and projects
  that reference it. With `PackageReference`, Newtonsoft.Json 13.0.1 flows from
  `BlogClient` into `PostEditor`, which asks for 10.0.2. `TreatWarningsAsErrors` makes it an error.
  The conversion should raise the direct version (the model has both) or report the conflict with
  its own code.
- **The scratch copy is not the working tree.** `ScratchWorktree` is a `git worktree` of `HEAD`, plus
  the model's inputs, compile items and the converted projects' folders. The model's inputs are the
  project files, `packages.config`, `Directory.Build.props` and the solutions, not imported files
  (`writer.build.settings`) and not `NuGet.config`. So uncommitted fixes to them are missing:
  - converting one project (`LocEdit`, `Localization`) fails with MSB3644 in its legacy
    dependencies, because the scratch copy has `HEAD`'s `writer.build.settings`;
  - restores in the scratch copy used the original v2 feed.

  The same omission means editing an imported `.props` or `.targets` file, or `NuGet.config`, does
  not make the model stale.
- **Conversion defects visible in the preview:**
  - A `PostBuildEvent` in a conditioned property group (the form `OFR0115`'s remedy produces)
    becomes an unconditioned `PostBuild` target: the condition is lost (the MSB3073 above).
    `LegacyProjectConverter.Tail` reads the property from every `PropertyGroup` and ignores the
    group's `Condition`.
  - `--tfm "net461;net10.0-windows"` does not set `UseWindowsForms` and keeps
    `<Reference Include="System.Windows.Forms" />` (and `System.Deployment`) unconditionally.
  - `writer.build.settings`, imported first in the legacy project, moves after the project body.
    It sets `TargetFrameworkVersion` and `OutputPath` unconditionally.
  - `<Target Name="_CopyFilesMarkedCopyLocal" />` in `CoreServices` overrides a common target. In an
    SDK-style project the SDK's definition comes later and wins, so copy-local silently returns.
    Only `BeforeBuild`/`AfterBuild` get `OFR4302`.
- **Fix:**
  - When the recorded compiler inputs contain version attributes in a file the converter does not
    edit, set `GenerateAssemblyVersionAttribute`/`GenerateAssemblyFileVersionAttribute` to false.
  - Resolve versions across the converted set.
  - Add imported project files (from the evaluation's import list) and `NuGet.config` to the model's
    inputs.
  - Keep a build event's group condition on the new target.
  - Set `UseWindowsForms`/`UseWPF` for `-windows` targets and condition framework references to the
    .NET Framework target.
  - Warn (`OFR4302`) for any target in the body whose name the common targets define, and for
    imports that set `TargetFrameworkVersion`, `OutputPath`, `IntermediateOutputPath` or
    `MSBuildExtensionsPath`.
- **General,** except the generated version file, whose mechanism is OLW's (the pattern, a shared
  generated version file, is common).

#### 10. `move extract` into a new `netstandard2.0` project plans nothing

`move extract --from OpenLiveWriter.CoreServices --new OpenLiveWriter.CoreServices.Portable --tfm
netstandard2.0 --files 'src/managed/OpenLiveWriter.CoreServices/Progress/*.cs'` (12 files with no
audit finding) plans 0 moves. It reports `OFR2104` ×11, "OpenLiveWriter.CoreServices does not
compile without the moved files, so nothing moves". The details are CS0012: "The type 'Exception'
is defined in an assembly that is not referenced. You must add a reference to assembly
'netstandard, Version=2.0.0.0'".

`MovePlanner.SourceCheck` adds the destination's trial compilation to the recorded `net461`
compilation, without the `netstandard.dll` facade that MSBuild's `ImplicitlyExpandNETStandardFacades`
adds in a real build. DotNetNuke's Library already referenced `netstandard2.0` projects, so its
recorded compilation had the facade.

- **Fix:** when a .NET Framework source gains a reference to a .NET Standard destination, add the
  facades the build would add (`netstandard.dll` and the `System.*` facades, from the reference
  assemblies package or `Microsoft.NET.Build.Extensions`).
- One project-level failure is still reported once per file (DotNetNuke P2, still open).
- **General:** this blocks the first move out of every .NET Framework project that does not yet
  reference a .NET Standard project, which is the first step of an incremental migration.

## Appendix: what it took to build OLW on Linux

The items are in the order they were hit; each was one more `scan`. Item 3 is for this sandbox's
proxy, not for OLW.

1. **Solution.** `offramp init --defaults --solution src/managed/writer.sln --force`.
2. **`doctor --fix --apply --yes`**, as the README says. Then, in `writer.build.settings`, add
   `Condition="'$(OS)' == 'Windows_NT'"` to the `MSBuildExtensionsPath` and
   `MSBuildExtensionsPath32` properties, so `Directory.Build.props` is imported (P1 #5).
3. **Sandbox only:** `NuGet.config` names `https://nuget.org/api/v2/`, whose downloads redirect to
   `globalcdn.nuget.org`, blocked here. The packages the build adds were first fetched into the
   global packages folder with a throwaway project against `api.nuget.org/v3`. After `deps audit`,
   `NuGet.config` was pointed at `https://api.nuget.org/v3/index.json`.
4. **Non-string resources (`OFR0119`).** In `Directory.Build.props`, for
   `'$(OfframpCompileOnly)' == 'true'`: `GenerateResourceUsePreserializedResources=true`, a
   `PackageReference` to `System.Resources.Extensions` 6.0.0 (`IsImplicitlyDefined="true"`), and, for
   legacy projects, `<Reference Include="System.Resources.Extensions"><HintPath>$(NuGetPackageRoot)system.resources.extensions/6.0.0/lib/net461/System.Resources.Extensions.dll</HintPath></Reference>`.
5. **Letter case in `.resx`.** In `src/managed/OpenLiveWriter.Localization`, a `commandbitmaps/` folder
   holding a lower-case symlink to every file in `CommandBitmaps/` (58 references differ in case).
6. **Letter case (`OFR0117`).** Symlink `intl/markets/Master.xml` → `master.xml`.
7. **Build-time generator (`OFR0115`).** Add `Condition="'$(OfframpCompileOnly)' != 'true'"` to the
   `GenerateMarketXmlImpl` target in `OpenLiveWriter.CoreServices.csproj`, and write
   `Marketization/Markets.xml` once by compiling `src/managed/MarketXmlGenerator/MarketXmlGenerator.cs`
   into a `net10.0` console app and running it on `intl/markets`.
8. **`Microsoft.Bcl.Build`.** `offramp.yml`: `verify.properties: { SkipEnsureBindingRedirects: "true" }`.
9. **Letter case (`OFR0117`).** Symlink `src/managed/OpenLiveWriter.PostEditor/Video/YouTube` →
   `Youtube`.
10. **Native project.** Delete the line
    `{195A60BF-7A4D-42E6-B5F4-FEBC679E19F0}.Debug|Any CPU.Build.0 = Debug|Win32` from `writer.sln`, so
    the Ribbon project is not built and the application, which depends on it at solution level, is
    (P1 #7).
11. **Installer post-build event (`OFR0115`).** Add `Condition="'$(OfframpCompileOnly)' != 'true'"` to
    the property group holding `PostBuildEvent` in `PostBuild.CreateInstaller.csproj`.
12. **MSTest v1.** In `Directory.Build.props`, for `OpenLiveWriter.UnitTest` and
    `OpenLiveWriter.Tests`, references to `MSTest.TestFramework` 1.4.0's
    `Microsoft.VisualStudio.TestPlatform.TestFramework.dll` and `.Extensions.dll` through
    `$(NuGetPackageRoot)`.

The `audit api` root cause (P0 #1) was confirmed with a second model in which the 18 projects that
use WinForms but are not `WinExe` were given `kind: winforms` in `offramp.yml` (`projects:`); the
native-project result (P1 #8) with another model scanned from the as-shipped binary log.
