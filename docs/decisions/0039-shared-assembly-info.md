# 0039. Leave shared and generated AssemblyInfo files alone

- Status: accepted
- Date: 2026-09-29
- Spec section: `docs/spec/commands/scaffold.md#csproj-modernize`, `docs/spec/commands/codemod.md` (`assemblyinfo`)

## Context

`csproj modernize` removes the assembly attributes the SDK generates with the `assemblyinfo`
codemod and moves their values into project properties. The codemod rewrote every compile item
of the project, linked files included. Three field tests found what that does to a file the
project does not own:

- NHibernate 4.1.2 links `src/SharedAssemblyInfo.cs`, which the NAnt build writes and git ignores,
  into six projects, one of them outside the solution. The edit did not show in `git status`, and
  the next NAnt build wrote the attributes back, so the SDK's generated ones collided (CS0579).
- SmartStoreNET 4.2.0 links `src/AssemblyVersionInfo.cs` and `src/AssemblySharedInfo.cs` into
  19 projects; 14 are web projects `csproj modernize` refuses to convert. They would have built as
  version 0.0.0.0, and verification, which builds only the converted projects, could not notice.
- Open Live Writer 0.6.3 converts one project at a time (the guide's port step), so every step
  stripped `GlobalAssemblyInfo.cs` for the 19 projects still legacy. Its build also writes
  `GlobalAssemblyVersionInfo.cs` and adds it to the compilation in a target, so the file is not a
  compile item of any project: the codemod never saw it, and the SDK's version attributes
  duplicated it in 20 projects.

The spec said which attributes go, not whose file they may be taken from.

## Decision

The `assemblyinfo` codemod (in `codemod run` and in `csproj modernize`) edits only the project's
own AssemblyInfo files. A file with attributes the SDK generates is left as it is when it is
outside the project's folder, compiled by another project of the workspace model, ignored by git
(`git check-ignore`: a build output), added to the compilation by a build target rather than the
project file, or generated code (an `<auto-generated>` header or a `.g.cs` name, which analyzers
do not look at, so the driver checks those files itself). For each attribute such a file declares,
the project sets `GenerateAssembly<Name>Attribute` to `false` (unless it already sets that
property), so the SDK does not generate it again, and `OFR4306` names the file and why. A file
compiled only by projects converted in the same run is still left alone.

## Alternatives considered

- `GenerateAssemblyInfo=false` when the shared files declare every attribute the SDK generates.
  It is shorter, but it also turns off what SDK-style projects declare as items and properties
  (`InternalsVisibleTo` items, `AssemblyMetadata`, `NeutralLanguage`, the platform attributes of
  `-windows` targets), so a later edit to the project would silently do nothing. The per-attribute
  switches turn off exactly what the file declares.
- Edit a shared file when every project that compiles it is converted in the same run. It saves the
  switches in that one case, but a file can still be generated or compiled by a project outside the
  model (NHibernate's `HbmXsd`), and the run would have to prove every sharer builds before editing.
  Moving a solution-wide version into `Directory.Build.props` is a decision for the user, once every
  project is SDK-style.
- Only report the shared file. The conversion would then fail verification with CS0579 for every
  attribute the file declares.

## Consequences

Conversions of solutions versioned by a shared or generated file keep that versioning, and build.
The converted projects carry a few `GenerateAssembly…Attribute` properties until the user moves the
version into properties for all projects and deletes the file; `OFR4306`'s fix says how. `codemod
run --mod assemblyinfo` asks git once per project with sites; outside a git repository nothing is
treated as ignored.
